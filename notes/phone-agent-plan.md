# Aynur 手机 Agent 路线草案

更新：2026-10-26。用户已明确 Android 优先，同时保留陪伴为核心能力，通过服务和手机系统能力帮助办事；第一项执行任务是用维语指挥手机打电话。本文件描述后续方案，不代表拨号及所有陪伴增强功能已经实现。

## 产品方向

**能用维语陪人聊天、准确进行维汉互译，并在需要时帮人办事的 Android 助手。** 陪伴、双向翻译与任务执行均为核心能力，妹妹的声音继续作为统一音色方向。

用户可以闲聊、倾诉、追问或讲日常，也可以明确提出任务。Aynur 理解任务、调用手机或服务能力，再用维语反馈实际结果。陪伴能力与首项拨号任务共同进入第一版。

目标人群暂沿用维语使用者、家里长辈。此前“自用 + 作品集”的开发阶段继续适用；手机 Agent 方向本身不代表已决定商业化、公开上线或全天候部署。

## 当前基础与缺口

| 部分 | 当前情况 | 下一步 |
|---|---|---|
| 语音识别、对话、语音合成 | 已有本地 ASR、模型接口、妹妹音色 TTS | 增加任务意图、参数理解及结果播报 |
| 客户端 | PWA，可录音、显示回答及播放语音 | 若要使用手机系统能力或操作其他 App，增加 Android 原生客户端 |
| 模型调用 | 当前只接收生成文本，没有工具执行链路 | 增加结构化工具调用、参数验证、结果回传 |
| 数据记录 | 会话、档案、用量、失败事件 | 增加任务状态、执行证据、耗时和失败原因 |
| 手机操作 | 尚未实现 | 根据首批具体任务选执行方式，并在目标手机验收 |
| 维汉翻译 | 已有对话中转用双向翻译组件，尚无独立翻译产品验收 | 增加忠实翻译入口、双语对照及双向质量评测；中文语音输入另需接入 |

## 核心能力一：维语陪伴

- **日常聊天**：聊家常、听用户讲当天的事，能围绕同一话题继续追问；回答口语化、温和，避免每轮都重复自我介绍或机械安慰。
- **情绪回应**：用户说无聊、想念家人或心情不好时，先回应表达，再自然接话。情绪表达本身不触发拨号。
- **熟悉感**：沿用现有称呼、人设和家人档案，让语气保持一致。自动提取并长期记住聊天事实属于后续增强，不能把现有档案字段等同于完整长期记忆。
- **打开问候**：沿用首次打开问候的方向，陪伴可从用户打开 App 时自然开始。首版主动性继续按 D3，不额外增加后台推送。

当前已有多轮对话链路、人设提示词和可配置档案；真实长辈对话的自然度、维语发音和上下文连续性仍需验收。

## 核心能力二：手机任务执行

从维语拨号切入，后续按需求扩展天气、提醒与信息查询。任务执行与闲聊共用一个语音入口，不要求用户切换“聊天模式”和“办事模式”。

交互衔接：

- “我想妈妈了” → 陪用户聊，可以询问是否想联系家人；未获明确指令时不创建呼叫。
- “帮我给妈妈打电话” → 进入联系人匹配和拨号确认流程。
- “给她打个电话” → 根据当前话题确认“她”指谁，不凭猜测选择联系人。
- “算了，不打了” → 取消待执行任务，再继续对话；不让聊天中的“嗯”“好”触发已经取消或过期的呼叫。

## 核心能力三：准确的维汉双向翻译

2026-10-26 用户明确要求维吾尔语与汉语之间准确互译。翻译与陪伴、手机办事共同进入核心规划；准确性是待评测的目标，不能仅因接入模型就宣称达标。

首版建议支持维文与中文文本互译，显示原文与译文并可复制；逐步接入“说维语 → 中文译文”和“说汉语 → 维语译文”的语音流程，提供源语言和目标语言选择，自动判断不确定时询问用户。译文朗读按对应语音能力验收。

翻译原则：

- 忠实保留事实、否定、条件、时间、数量、单位、人物关系和语气，不擅自删减、补充或替用户回答问题。
- 人名、地名、药名、亲属称呼等使用经校对的术语；未知专名保留原文或明确待确认，不凭空编造。
- 原文有歧义时请求澄清或提供明确标注的不同解释，不用模型自报的置信度作为准确保证。
- 原文和译文分开呈现，额外解释单列。陪伴人格不改写原文含义，普通翻译请求不走聊天中的安慰或分类兜底话术。
- “把‘给妈妈打电话’翻成汉语”只产生译文，不能触发拨号；待翻译内容是数据，不是执行指令。

现有技术边界：`server/providers/mt.py` 为 B 类对话链路服务，汉译维提示词偏口语化且输出长度有限，需要为独立翻译设计忠实度规则与长度处理。当前本地 ASR 为维语模型，中文语音输入需另接中文识别；已验证的妹妹音色只覆盖维语，中文同音色合成仍需验证，不能宣称已有双语克隆能力。长文本逐段翻译与朗读时须保持顺序并检测遗漏或截断。

准确性验收建议：

1. 维译汉、汉译维各准备至少 30 条人工校对样本，覆盖日常交流、数字时间、否定、条件、亲属称谓与专名；调试样本和最终验收样本分开。
2. 双语评审逐句检查意思是否完整准确，再评自然度；单列数字、单位、否定和对象错误。回译和模型评分只作辅助，不能代替人工判断。
3. 对比现有通用模型与专用翻译模型，以同一批样本决定路线，不预设某模型一定更准。
4. 文本通过后再验语音，分别记录识别、翻译和播报错误，避免把听写错误归因于翻译模型。
5. 发布样本中的关键意义错误需修复后复验；报告实际通过条数、错误类别和适用场景，不承诺所有输入都百分之百准确。

## 首项任务：维语拨号

用户确认的范围：Android 优先，以工具与服务接入为主。首项任务为听懂维语拨号指令，解析联系人或电话号码，确认后交给手机系统执行。

建议交互：用户用维语说“给妈妈打电话” → 在手机匹配已绑定的联系人 → 用妹妹音色确认姓名、号码尾号 → 用户语音确认 → 请求系统呼出。找不到联系人、重名或有多个号码时先补问；用户说取消时终止当前任务。

实现建议：

- 首版允许由家人预先绑定几个常用联系人和维语亲属称呼；系统通讯录导入作为可选能力，按需授权。联系人匹配优先留在手机端，避免把整本通讯录传给模型。
- Android 小型原生客户端承接录音、播放、确认和拨号；复用现有 FastAPI 与 ASR/TTS。
- 原型先采用 App 前台语音入口，不把后台唤醒、锁屏呼出或通话录音作为首项任务要求。
- `ACTION_DIAL` 可打开填好号码的拨号页，用户仍需点击拨号；`ACTION_CALL` 可请求直接呼出，需要电话权限及运行时授权。以用户语音确认后请求呼出为目标，未授权时明确说明并提供拨号页入口。
- 联系人和号码必须来自用户输入或本机已确认数据；执行端检查号码、工具名和当前确认状态，不直接执行模型任意输出的动作。
- 只能报告观察到的状态：已打开拨号页、已请求呼出或执行失败。基础电话状态不能证明对方实际接听，不能据此播报“已接通”。

首项验收：常用联系人、直接说号码、重名补问、取消、权限未授予、无可用拨号处理程序等场景。真实呼叫与通话费用需在用户操作确认下进行；自动测试用模拟执行端。

## 建议架构

手机负责录音、展示、设备权限和本机工具执行。现有 FastAPI 负责语音识别、任务理解、调用服务和维语语音合成；执行结果回传后才能生成完成反馈。

这条原型路线仍可使用现有电脑 GPU。它不是完全在手机本地运行的方案；手机需要能够连接后端，不能直接使用电脑的 `localhost` 地址。独立于电脑的使用方式另行评估，不能把现有 CUDA 模型直接视为已适配手机。

按具体任务选择工具：

1. 查询与服务任务优先接 API，获得可检查的返回结果。
2. 打开应用、跳转地图、调用系统闹钟等，优先评估 Android Intent 或对应系统接口。
3. 需要在其他 App 页面里多步操作时，再评估无障碍服务或屏幕交互；先在目标手机、目标 App 上验证可行性。

普通 PWA 无法单独控制整部手机。封装 WebView 也需要实现相应原生能力，不会自动获得跨 App 执行能力。

## 任务闭环

理解需求 → 补齐参数 → 执行 → 观察结果 → 维语反馈。

- 信息不足时询问缺失项，例如联系人有多个或时间不明确。
- 区分“理解了”“已打开页面”“等待用户操作”“已完成”“失败”“已取消”。
- 工具调用成功不等于用户任务完成。只打开地图页时，就反馈已打开地图，不能说已到达或已开始导航。
- 外发消息或拨号等场景，在明确对象和内容后设计确认步骤；首批范围以用户选择为准。
- 执行可取消，超时停止；再次执行前检查是否可能重复提交。
- 其他 App 的页面、消息与网页内容作为任务数据处理，不据此擅自切换用户目标。

## 其他候选任务（暂未排入首项开发）

| 示例指令 | 可从哪里开始 | 验收时需要区分 |
|---|---|---|
| 打开微信 | Android 应用启动 | 已打开应用与已进入指定联系人页面 |
| 明早七点叫我 | 系统闹钟接口或 Intent | 已打开设置页与闹钟实际已建立 |
| 帮我查明天天气并念出来 | 天气服务和现有 TTS | 日期、城市、天气数据及播报是否一致 |
| 帮我给家人发一句话 | 消息草稿、分享流程；进一步自动化另评估 | 草稿已生成、分享页已打开与消息实际发送 |
| 带我去附近医院 | 地图跳转或地图服务 | 已展示候选、已打开路线与导航实际启动 |

先完成维语拨号，再从这些示例中选择扩展场景，不是整批开发承诺。

## 微信能力边界（2026-10-26 核对）

微信官方移动应用接口支持将文字、图片等内容分享至会话等场景，需申请移动应用并通过相应审核。该能力不能等同于用个人账号任意读取聊天、指定联系人后台自动发消息、自动发起微信通话。

本次核对的官方接口未提供通用个人聊天 Agent 的执行入口。可以后续评估“生成内容 → 唤起微信分享 → 用户选择与确认”；跨 App 页面自动操作需要单独验证，不作为当前承诺。

## 实施顺序与验收

1. 为 Android 维语拨号定义意图、联系人参数、确认与执行结果；手机具体型号和系统版本在真机验收前补充。
2. 做一个最小竖向闭环：维语指令 → 参数 → 手机确认 → 系统拨号 → 结果反馈。缺工具时明确返回不支持，不能模拟完成。
3. 加入重名补问、取消和权限失败反馈，验收通过后再扩展天气、提醒或信息查询。
4. 用固定测试指令记录理解正确率、任务完成率、耗时及失败原因，保留真实手机演示。

陪伴同步验收：至少覆盖日常闲聊、情绪倾诉、连续追问、聊天转拨号、指代不明、取消后继续聊天。分别检查有没有接住话题、有没有误触发任务，以及播报是否自然完整；任务完成率不能代替陪伴质量。

翻译同步推进：先完成双向文本评测与独立翻译流程，再补中文语音识别和双语播报；三类意图共同验收，确保聊天、翻译和执行任务不会混淆。
